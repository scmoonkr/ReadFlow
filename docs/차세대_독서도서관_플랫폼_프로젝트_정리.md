# 독서 중심 차세대 도서관 플랫폼 프로젝트 정리

## 1. 프로젝트 개요

기존의 자료관리·회원관리·대출·수서·통계 중심 도서관리시스템에서 벗어나, **책·독자·도서관을 중심으로 발생하는 관계와 활동을 연결하는 독서 중심 플랫폼**으로 전환한다.

> **도서관의 장서를 관리하는 시스템에서 독자의 독서 세계를 연결하는 시스템으로 전환**

플랫폼은 도서관 업무를 단순히 디지털화하는 것에 머무르지 않고 다음을 함께 지원한다.

- 공통 책 정보 관리
- 도서관·개인별 책 관리
- 실제 소장책 관리
- 회원과 도서관의 관계 관리
- 대출·반납·예약·수서 등 도서관 업무
- 독자의 읽기·기록·추천·모임 활동
- 현재 상태 관리
- 활동 이력과 분석
- 추천과 새로운 관계 생성

---

# 2. 핵심 설계 철학

## 2.1 Entity + Relationship + Transaction + State + Event

전체 시스템은 다음 관점으로 본다.

### Entity
누가/무엇이 존재하는가

- Book
- Reader
- Library
- Person
- Subject
- Group
- Holding

### Relationship
서로 어떤 관계인가

- Reader ↔ Library Membership
- Reader ↔ Book Reading
- Library ↔ Book LocalBook
- Reader ↔ Book Personal LocalBook
- LocalBook ↔ Holding

### Transaction
실제 업무 데이터

- Loan
- Reservation
- Request
- Order
- Purchase
- Membership
- Reading

### State
현재 어떠한가

- Holding: AVAILABLE / LOANED / LOST
- Membership: ACTIVE / SUSPENDED
- Request: REQUESTED / APPROVED / RECEIVED
- Reading: WANT_TO_READ / READING / FINISHED

### Event
무슨 변화가 있었는가

- LOAN_CREATED
- LOAN_RETURNED
- HOLDING_LOST
- MEMBERSHIP_SUSPENDED
- REQUEST_APPROVED
- START_READING
- FINISH_READING

핵심 원칙:

```text
Transaction = 업무
State       = 지금
Event       = 변화의 기록
```

현재 업무 처리를 위해 필요한 상태는 각 객체에 직접 저장하고, 의미 있는 변화는 Event 또는 History로 별도 기록한다.

현재 상태를 매번 과거 Event에서 다시 계산하지 않는다.

---

# 3. MARC의 역할

MARC는 내부 데이터베이스 구조가 아니라 **서지정보 교환·입출력 형식**으로 사용한다.

```text
MARC Import
    ↓
Parser / Mapping
    ↓
Global Book Model
    ↓
JSON / API / AI / MARC Export
```

원칙:

- MARC 태그를 그대로 DB 컬럼으로 만들지 않음
- 실제 의미 중심 내부 모델로 변환
- 내부 모델로 표현하기 어려운 값은 원본 보존 영역에 유지
- MARC는 외부 입출력 호환 포맷으로 사용

---

# 4. 핵심 책 데이터 구조

현재 핵심 구조는 다음 3계층으로 정리한다.

```text
Global Book Master
        ↓
Local Book Master
        ↓
Holding
```

각 계층의 역할을 명확히 분리한다.

---

# 5. Global Book Master

## 5.1 역할

플랫폼 전체에서 공통으로 사용하는 대표 책 정보.

```text
GlobalBook

book_id
title
author
publisher
isbn
publication_date
price
edition_statement
pages
size
cover
summary
toc
subject
classification
...
```

GlobalBook은 여러 도서관과 개인이 공통으로 사용한다.

같은 책의 기본정보를 각 도서관과 개인이 반복 저장하지 않는다.

---

## 5.2 ISBN 처리

ISBN은 매우 중요한 식별자이지만 시스템의 최종 고유 ID는 아니다.

```text
book_id = 시스템 내부 고유 ID
isbn    = 검색·매칭용 식별정보
```

원칙:

- ISBN은 실무적으로 거의 고유하게 사용
- DB에서는 반드시 UNIQUE로 강제하지 않음
- 같은 ISBN의 기존 Book이 있으면 기본적으로 기존 Book 사용
- 실제 다른 책임이 확인된 희귀한 경우 동일 ISBN으로 새 GlobalBook 생성 허용
- 이후 LocalBook, Holding, Reading 등 모든 관계는 ISBN이 아닌 `book_id` 사용

검색 처리:

```text
ISBN 검색

0건
→ 신규 Book 후보

1건
→ 해당 Book 사용

2건 이상
→ ISBN 충돌 예외 화면
```

희귀한 ISBN 재사용 문제 때문에 전체 모델을 복잡하게 만들지 않는다.

---

# 6. Edition History

Edition은 GlobalBook과 Holding 사이의 필수 계층으로 사용하지 않는다.

Edition은 **책의 출판 변천사를 관리하는 History Collection**으로 둔다.

예:

```text
Global Book: A책

Edition History
├─ 2021.01.01 / 초판 / 13,000원 / 304p / 148×210
└─ 2022.02.01 / 2판 / 13,500원 / 320p / 152×225
```

목적:

- 전체 출판 이력 보존
- 운영자 참고
- 서지정보 변화 확인
- 필요 시 로컬·소장 입력 보조

Holding과 Edition History를 반드시 FK로 연결하지 않는다.

실제 소장책의 판정보가 필요하면 Holding에 직접 기록한다.

# 7. Global Book 등록 및 운영

## 7.1 신규 책 등록 흐름

Local에서 필요한 책이 Global에 없는 경우:

```text
Local에서 책 추가
    ↓
Global 검색
    ↓
없음
    ↓
최소 기본정보 입력
    ↓
Temporary Global Book 생성
    ↓
Local Book 생성
    ↓
Holding 생성
    ↓
운영자에게 보완 요청
```

최소 입력 예:

- 서명
- 저자
- ISBN
- 출판사
- 출간일
- 정가
- 형태사항

GlobalBook 상태 예:

```text
PENDING
VERIFIED
ACTIVE
MERGED
ARCHIVED
```

운영자 승인 전이라도 Local Book 등록과 소장·대출 업무는 가능하게 한다.

---

## 7.2 Global Book 수정 권한

GlobalBook은 플랫폼 운영자가 관리한다.

Local 사용자는:

- GlobalBook 검색
- 없는 경우 최소정보 등록
- 수정·보완 요청

운영자는:

- 서지 보완
- 외부 데이터 확인
- Edition History 관리
- Merge / Split
- 오류 수정

---

# 8. Merge / Split

GlobalBook DB는 운영자가 구축·관리하므로 실제 Merge/Split은 빈도가 낮을 것으로 본다.

따라서 일상 업무 기능이 아니라 **운영자 Batch 관리 기능**으로 둔다.

### Merge

```text
Book #100
Book #235
    ↓
MERGE
    ↓
Book #100
```

관련 LocalBook 및 관계의 book_id를 Batch 처리한다.

### Split

잘못 합쳐진 경우:

```text
Book #100
    ↓
SPLIT
    ↓
Book #100
Book #902
```

Merge / Split 이력은 반드시 기록한다.

---

# 9. Local Book Master

## 9.1 역할

도서관과 개인이 GlobalBook에 대해 별도로 관리하는 로컬 책 정보.

도서관과 개인은 **동일한 기본 LocalBook 구조**를 사용한다.

```text
LocalBook

local_book_id
owner_type
owner_id
book_id
local_classification
local_subject
local_tags
local_memo
...
```

```text
owner_type
- LIBRARY
- READER
```

---

## 9.2 Global Fallback

LocalBook에서 별도로 관리하지 않는 항목은 GlobalBook 값을 사용한다.

예:

```text
GlobalBook
분류: 문학
주제: 성장 / 프랑스 문학

LocalBook
분류: 863
주제: null
```

최종 표시:

```text
분류 → Local 863
주제 → Global 성장 / 프랑스 문학
```

원칙:

```text
Local 값이 있으면 Local
Local 값이 없으면 Global
```

Global 값을 Local에 불필요하게 복제하지 않는다.

---

## 9.3 Local 정보 예

### Library

- 자체 분류
- 로컬 주제
- 청구기호
- 로컬 태그
- 컬렉션
- 메모

### Reader

- 개인 분류
- 개인 주제
- 태그
- 메모
- 개인 컬렉션

기본 구조는 같고 필요한 속성만 사용한다.

# 10. Holding

## 10.1 정의

Holding은 **실제로 존재하는 한 권의 책**을 의미한다.

원칙:

> **한 권이라도 반드시 Holding으로 관리한다.**

```text
GlobalBook
    ↓
LocalBook
    ↓
Holding
```

도서관과 개인 모두 동일한 원칙을 사용한다.

---

## 10.2 Holding의 역할

```text
Holding

holding_id
local_book_id

accession_number
barcode
location
acquired_at
purchase_price
status

edition_statement_override
publication_date_override
price_override
pages_override
size_override
...
```

도서관에서는 등록번호가 실제 책 한 권의 주요 식별자가 된다.

대출·반납은 Holding 자체에 저장하지 않고 **holding_id를 사용하여 Loan Transaction에서 처리한다.**

---

## 10.3 판이 다른 복본 처리

일반적인 경우 LocalBook은 Global 대표 정보를 사용한다.

같은 ISBN이지만 실제 소장한 특정 한 권의 판사항이 다른 경우:

```text
LocalBook: A책

Holding #10001
판정보 없음
→ Global / Local 대표정보 사용

Holding #10002
판정보 없음
→ Global / Local 대표정보 사용

Holding #10003
판사항: 초판
발행일: 2021
가격: 13,000
페이지: 304
```

즉 **예외적인 차이만 Holding에 기록**한다.

---

# 11. 소장과 독서의 분리

소장과 독서는 서로 다른 관계다.

```text
Reader ─ owns ─ Holding
Reader ─ reads ─ GlobalBook
Reader ─ borrows ─ Holding
```

친구나 도서관 책을 빌려 읽을 수도 있으므로:

```text
소장 ≠ 대출 ≠ 독서
```

독서 활동은 기본적으로 GlobalBook을 대상으로 한다.

---

# 12. Reader

Reader는 특정 도서관의 회원으로 종속시키지 않는다.

```text
Reader
├─ Membership → Library A
├─ Membership → Library B
├─ Personal LocalBook
├─ Reading → GlobalBook
├─ Recommendation → GlobalBook
└─ Group Participation
```

핵심 원칙:

> **회원은 독자의 정체성이 아니라 독자와 도서관 사이의 관계다.**

---

# 13. Membership

도서관은 자체 회원번호를 계속 관리한다.

시스템에서는 Reader와 Library의 관계를 Membership으로 표현한다.

```text
Membership

membership_id
reader_id
library_id
member_no
joined_at
status
...
```

예:

```text
Reader #100

Membership A
library = A도서관
member_no = A12345

Membership B
library = B도서관
member_no = B78901
```

회원번호는 Reader ID가 아니다.

# 14. State / Transaction / Event

## 14.1 기본 개념

```text
State       = 지금 어떤 상태인가
Transaction = 실제 업무
Event       = 어떤 변화가 있었는가
```

예:

```text
Holding.status = LOANED
    ← State

Loan #500
    ← Transaction

LOAN_CREATED
    ← Event
```

---

## 14.2 대출 예


```text

```

```text

```

```text
Loan.returned_at 기록

```


# 15. Event 기록 원칙

모든 DB UPDATE를 Event로 기록하지 않는다.

의미 있는 업무·독서 변화만 Event 또는 History로 남긴다.

예:

### 도서관 업무

- HOLDING_REGISTERED
- LOAN_CREATED
- LOAN_EXTENDED
- LOAN_RETURNED
- RESERVATION_CREATED
- HOLDING_LOST
- HOLDING_RECOVERED
- MEMBERSHIP_CREATED
- MEMBERSHIP_SUSPENDED
- REQUEST_CREATED
- REQUEST_APPROVED
- BOOK_RECEIVED

### 독서 활동

- WANT_TO_READ
- START_READING
- READING_PROGRESS
- FINISH_READING
- REVIEW_CREATED
- RECOMMEND_CREATED

사소한 오타 수정 등은 일반 변경 로그만으로 충분할 수 있다.

# 16. 삭제 정책

기본적으로 실제 DELETE보다 **상태 변경**을 우선한다.

예:

### Holding

```text
ACTIVE
LOST
WITHDRAWN
DISCARDED
TRANSFERRED
```

### LocalBook

```text
ACTIVE
INACTIVE
ARCHIVED
```

### GlobalBook

```text
PENDING
ACTIVE
MERGED
ARCHIVED
```

### Membership

```text
ACTIVE
SUSPENDED
EXPIRED
WITHDRAWN
```

과거 Loan, Event, Analytics가 유지되어야 하기 때문이다.

실제 DELETE는 테스트 데이터, 즉시 취소된 잘못된 생성, 법적으로 필요한 개인정보 삭제 등 특별한 경우에 제한한다.

# 17. 전체 핵심 데이터 구조

```text
                    Global Book Master
                     공통 책 정보
                           │
             ┌─────────────┴─────────────┐
             │                           │
     Library LocalBook           Reader LocalBook
       도서관 책정보                개인 책정보
             │                           │
       ┌─────┼─────┐               ┌─────┼─────┐
       ▼     ▼     ▼               ▼     ▼     ▼
    Holding Holding Holding      Holding Holding Holding
      실제책  실제책  실제책        실제책  실제책  실제책
       │
       └──── Loan / Return / Reservation
```

독서 구조:

```text
Reader
   │
   ├─ WANT_TO_READ → GlobalBook
   ├─ START_READING → GlobalBook
   ├─ FINISH_READING → GlobalBook
   ├─ REVIEW → GlobalBook
   └─ RECOMMEND → GlobalBook
```

회원 구조:

```text
Reader
   │
   ├─ Membership → Library A
   └─ Membership → Library B
```

# 18. 독서 진행 상태

종이책에서는 정확한 진행률 자동 수집이 어렵다.

독자에게 지속적인 페이지 입력을 강요하지 않는다.

기본 상태:

```text
읽고 싶어요
↓
읽기 시작
↓
읽는 중
↓
다 읽었어요
```

선택 기능:

```text
조금 읽었어요
절반쯤 읽었어요
거의 다 읽었어요
다 읽었어요
```

원하면:

```text
82 / 194쪽
```

처럼 직접 기록할 수 있다.

핵심 원칙:

> **사서의 입력 부담을 없애면서 그 부담을 독자에게 옮기지 않는다.**

# 20. 핵심 UX 원칙

1. 내부 DB 구조를 사용자에게 보여주지 않는다.
2. 메뉴보다 현재 대상(Entity)과 다음 행동을 우선한다.
3. Global / Local / Holding 차이는 필요한 순간에만 보여준다.
4. 정상적인 경우는 단순하게 처리하고 예외는 펼쳐서 처리한다.
5. 현재 State를 먼저 보여주고 Event는 이력으로 보여준다.
6. 독자 UX는 발견→읽기→기록→연결의 흐름으로 만든다.
7. 사서 UX는 해야 할 일과 현재 상태 중심으로 만든다.
8. 정보 입력은 최소화한다.
9. Reader와 Backend는 같은 Design System을 공유하되 정보 밀도는 다르게 한다.
10. **Simple by default, detailed when needed.**

# 38. 핵심 설계 원칙 최종 정리

1. MARC는 내부 DB가 아니라 교환 형식으로 사용
2. 책 기본정보는 Global Book Master에서 공통 관리
3. ISBN은 강력한 식별자이지만 절대적 Unique Key로 강제하지 않음
4. Edition은 필수 계층이 아니라 GlobalBook의 출판 이력으로 관리
5. 도서관과 개인은 동일한 Local Book 구조 사용
6. Local에 값이 없으면 Global 값을 사용
7. 실제 책 한 권마다 Holding 생성
8. 판이 다른 소장본은 Holding에 예외정보 기록
9. 대출·반납은 Holding ID를 대상으로 처리
10. Reader는 독립 Entity
11. Membership은 Reader와 Library의 관계
12. 회원번호는 도서관 로컬 정보
13. 현재 업무 State는 직접 저장
14. 의미 있는 변화는 Event / History로 기록
15. 모든 DB 변경을 Event로 만들지 않음
16. 삭제보다 상태 변경을 기본으로 함
17. 소장·대출·독서는 서로 다른 개념
18. 독서활동은 기본적으로 GlobalBook 기준
19. 내부 데이터 구조를 사용자에게 직접 노출하지 않음
20. Reader는 독서 흐름 중심
21. Librarian은 현재 상태와 해야 할 일 중심
22. 운영자는 GlobalBook과 데이터 품질 관리
23. 예외 상황 때문에 정상 업무를 복잡하게 만들지 않음
24. 불필요한 입력을 사서나 독자에게 요구하지 않음
25. DB 구조와 UI를 함께 검증
26. 전체 Conceptual Schema를 잡고 파일럿 범위만 상세 설계

---

# 39. 한 문장으로 정리

> **책의 공통 지식은 Global Book Master에서 관리하고, 도서관과 개인은 Local Book Master를 통해 자신만의 분류·주제·태그를 관리하며, 실제 책은 한 권 단위의 Holding으로 관리한다. Reader는 도서관 회원에 종속되지 않는 독립 Entity이며 Membership을 통해 각 도서관과 관계를 맺는다. 현재 업무 상태는 직접 저장하고 중요한 변화는 Event로 남기며, UI에서는 이러한 내부 구조를 숨기고 독자에게는 발견·읽기·기록·연결의 흐름을, 사서에게는 현재 상태와 다음 업무를 중심으로 제공하는 독서 중심 차세대 도서관 플랫폼을 구축한다.**
